# 초텐·아메의 귀와 입은 앱이 직접 쥔다

skinclaude에 한·일 음성 대화를 붙이는 현실적인 구조는 하나다. 오버레이가 마이크와 스피커를 직접 소유하고, 렌더러 캡처와 발화 구간 검출(VAD) → 교체 가능한 음성 인식(STT) → 기존 Claude Code CLI 자식 프로세스 → 문장 단위 음성 합성(TTS) → 같은 렌더러에서 재생으로 잇는 캐스케이드다. Claude 모델은 오디오를 입출력하지 못하고, Claude Code의 `/voice`는 터미널 입력창 전용 받아쓰기이며, VoiceMode·ElevenLabs MCP 같은 기성 플러그인과 MCP는 터미널 세션에 음성을 덧붙이는 도구라 참고 구현으로만 쓸 수 있다. 듣기는 이 Mac에 한국어 모델이 이미 설치된 Apple SpeechTranscriber를 기존 `claudewin`처럼 Swift 헬퍼로 붙여 무료·온디바이스로 시작하고, 언어는 자동 감지보다 캐릭터별 기본값과 단축키로 정하는 편이 짧은 발화에서 안전하다. 말하기는 "한 목소리가 두 언어를 말하느냐"와 "일본어가 애니풍으로 귀엽냐" 중 무엇을 앞세우느냐로 엔진이 갈린다. 하루 300줄 기준으로 기본값은 프리셋 보이스를 두 언어에 함께 쓰고 자연어로 연기를 지시하는 Gemini 3.8 Flash TTS(유료 월 약 $9~13)이고, 목소리 동일성과 연기 품질을 더 원하면 ElevenLabs Voice Design과 Remix(월 약 $15~31), 일본어 애니풍이 먼저면 무료 로컬 VOICEVOX를 일본어에만 섞는다(월 약 $5). 어느 경우든 목소리는 텍스트 설계나 프리셋에서 출발하고, 실존 성우의 목소리를 복제하거나 닮게 만드는 길은 쓰지 않는다. 엔진보다 먼저 발목을 잡을 곳은 LaunchAgent가 ad-hoc 서명 Electron을 띄우는 지금 구조의 마이크 권한 귀속과 헤드폰 없는 스피커의 에코이므로, 반이중·토글형 푸시투토크로 시작한다. 한·일 인식 정확도와 캐릭터 음색 모두 이 조건에서 잰 공개 비교가 없으니, 아래 순위는 짧은 발화 받아쓰기 시험과 캐릭터별 블라인드 청취로 확정할 잠정안이다.

## 기성 음성 도구는 재사용할 수 없고 얇은 자체 루프가 답이다

재사용할 수 있는 기성 음성 기능은 없다. 현재 Claude API 모델은 모두 텍스트와 이미지를 받아 텍스트만 내놓는다 ([Claude Models overview](https://platform.claude.com/docs/en/about-claude/models/overview)). Claude Code의 `/voice`는 한국어를 포함한 20개 언어를 받아쓰지만 **대화형 입력창에 붙은 STT일 뿐 TTS가 없고**, 녹음을 Anthropic 서버로 보내며 claude.ai 계정으로 로그인해야 쓸 수 있다 ([Claude Code Docs: Voice dictation](https://code.claude.com/docs/en/voice-dictation)). 입력창이 없는 상주 `claude -p --input-format stream-json` 프로세스에는 붙일 자리가 없다. 바이너리 안의 내부 WebSocket 엔드포인트를 OAuth 토큰으로 직접 부르는 길은 비공개 API라 약관·변경 위험 때문에 뺀다. 그래도 그 기본값인 16 kHz mono PCM, 발화 끝점 판정 300 ms, 발화 종료 판정 1,000 ms는 VAD 설정의 출발점으로 쓸 만하다 ([로컬 확인: Claude Code 2.1.284 바이너리](file:///Users/dobedub/.local/share/claude/versions/2.1.284)). Claude 앱의 음성 모드는 Claude Code에서 쓸 수 없고 개발자 API도 없다 ([Claude Help Center: Use voice mode](https://support.claude.com/en/articles/11101966-use-voice-mode)).

스킬·플러그인·MCP 생태계도 런타임의 핵심이 되지 못한다. 기성품 대부분이 터미널의 Claude Code 세션에 음성을 덧붙이는 도구이기 때문이다. 가장 성숙한 **VoiceMode**(★1.4k, MIT, v8.12.0)는 Claude Code 플러그인 마켓플레이스로 설치되고 로컬 whisper.cpp와 Kokoro로 돈다 ([GitHub mbailey/voicemode](https://github.com/mbailey/voicemode)). 그러나 Kokoro 공식 보이스 목록에는 **한국어가 없다** ([HF Kokoro-82M VOICES.md](https://huggingface.co/hexgrad/Kokoro-82M/blob/main/VOICES.md)). ElevenLabs 공식 로컬 MCP는 2026-08-20 아카이브돼 호스티드 MCP로 넘어갔고, 결과를 파일로 만드는 방식이라 실시간 대화에 맞지 않는다 ([GitHub elevenlabs/elevenlabs-mcp](https://github.com/elevenlabs/elevenlabs-mcp)). 훅으로 양방향 음성을 붙이는 mcp-voice-hooks는 브라우저 Web Speech API로 받아쓰는데 ([GitHub mcp-voice-hooks](https://github.com/johnmatthewtennant/mcp-voice-hooks)), 이 API는 Electron에서 "network" 오류로 동작하지 않는다는 보고가 거듭 나왔다 ([electron#46143](https://github.com/electron/electron/issues/46143)). 구조도 맞지 않는다. MCP의 말하기 도구는 Claude가 말할 시점을 정하고 도구 호출 왕복을 한 번 더 거친다. 두 캐릭터의 목소리와 발화 우선순위를 앱이 한곳에서 통제해야 하는 마스코트와는 방향이 반대다. 이 도구들의 가치는 참고 구현에 있다. VoiceMode의 발화 잠금과 수동 턴 종료(skip-forward) ([VoiceMode releases](https://github.com/mbailey/voicemode/releases)), Claude Code를 고치지 않고 앞단에 음성 층만 두는 duck_talk ([GitHub dhuynh95/duck_talk](https://github.com/dhuynh95/duck_talk))이 우리 구조와 같은 방향이다. Smithery·mcp.so 같은 레지스트리까지 전수 조사하지는 못했다. 개발 중 후보 보이스의 시청용 샘플을 Claude Code 세션에서 뽑는 보조 도구로는 ElevenLabs 호스티드 MCP를 쓸 수 있다(추론).

실시간 음성-음성(S2S) 모델로 대화층을 통째로 바꾸는 길도 이 앱에는 맞지 않는다. Gemini 3.8 Live는 한국어를 지원하고 오디오 입력 1M 토큰당 $3, 출력 $12로 싸지만 ([Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing)), 외부 LLM의 텍스트를 넣어 순수 STT·TTS로만 쓰는 방법은 문서에 없다 ([Gemini Live API capabilities](https://ai.google.dev/gemini-api/docs/live-api/capabilities)). 그러면 두 마스코트의 페르소나·기억·도구를 Claude Code 밖에 한 벌 더 둬야 한다. 2026년 9월 API로 나온 GPT-Live-1은 백엔드 위임을 공식화했고, Pipecat의 client delegation으로 임의의 백엔드를 붙일 수 있다 ([Pipecat docs: OpenAI Live](https://docs.pipecat.ai/api-reference/server/services/s2s/openai-live.md)). 하지만 무음을 포함해 세션 내내 **분당 $0.05**가 과금되고 ([OpenAI: gpt-live-1](https://developers.openai.com/api/docs/models/gpt-live-1)), 세션 안에서 목소리를 바꿀 수 없어 캐릭터마다 세션이 따로 필요하다 ([DataCamp: GPT-Live-1 API](https://www.datacamp.com/tutorial/gpt-live-1-api)). 한국어·일본어를 지원하고 Claude를 언어 모델로 연결할 수 있는 Hume EVI 4-mini도 ([Hume EVI FAQ](https://dev.hume.ai/docs/speech-to-speech-evi/faq)) 대화층이 둘로 갈리는 문제는 같다. Claude가 두뇌로 남는 한 S2S가 줄여 주는 것은 맞장구의 즉시성뿐이다. 이는 턴이 끝나자마자 미리 렌더링한 짧은 채움말이나 효과음을 틀어 싸게 흉내 낼 수 있다.

음성 루프 프레임워크를 들이는 이득도 작다. Pipecat(★16.1k)은 Anthropic·ElevenLabs·Gemini Live와 데스크톱용 로컬 오디오 전송까지 갖췄지만 Python 3.11 이상의 사이드카가 필요하다 ([GitHub pipecat-ai/pipecat](https://github.com/pipecat-ai/pipecat)). LiveKit Agents는 Node 패키지와 한국어를 포함한 턴 감지 모델이 있지만 LiveKit 룸을 전제한다 ([LiveKit docs: Turn detector](https://docs.livekit.io/agents/logic/turns/turn-detector)). 어느 쪽이든 Claude Code CLI를 LLM 서비스로 감싸는 어댑터를 새로 써야 한다. 그래서 답은 **Electron 안의 얇은 자체 루프**다. 텍스트 원천은 이미 있다. 잡담용 상주 프로세스(chatd)는 stream-json으로 토큰 단위 `text_delta`를 흘리고 ([Claude Code Docs: Run programmatically](https://code.claude.com/docs/en/headless)), 지시 세션의 Stop 훅은 마지막 응답 전문(`last_assistant_message`)을 담아 오버레이의 로컬 HTTP 서버로 들어온다 ([Claude Code Docs: Hooks](https://code.claude.com/docs/en/hooks)). 이 텍스트를 한국어 종결어미와 한·일 구두점(`. ! ? … ~ 。 ！ ？`) 기준 증분 분할기로 끊어 TTS에 넘긴다. 음성 비서에는 50~100자 청크를 권하는 가이드가 있지만 ([Deepgram: TTS text chunking](https://developers.deepgram.com/docs/tts-text-chunking)), 첫 청크는 더 짧게 끊어야 첫 소리가 빨라진다. ElevenLabs의 WebSocket `stream-input`은 이 버퍼링을 대신해 주지만 기본 설정에서는 누적 120자가 쌓여야 첫 오디오를 만든다 ([ElevenLabs API: stream-input](https://elevenlabs.io/docs/api-reference/text-to-speech/v-1-text-to-speech-voice-id-stream-input)). 한두 문장짜리 마스코트 대사에는 자체 분할기가 낫다.

얼마나 말할지도 구조의 일부다. 알렉사 음성 디자인 가이드는 한 호흡에 말할 수 있는 길이를 넘기지 말라고 권한다 ([Amazon Alexa: Be brief](https://developer.amazon.com/en-US/alexa/alexa-haus/design-principles/be-brief)). 마스코트는 잡담 답과 리액션, 이벤트 알림의 한두 문장만 소리 내고, 긴 답의 본문은 지금처럼 말풍선이 맡는다. 훅 이벤트는 우선순위 큐로 음성화한다. 권한 요청은 짧은 음성과 효과음으로 기다리던 나레이션을 앞지르고, 작업 완료는 한두 문장 요약으로, 잦은 도구 사용은 무음이나 짧은 효과음으로 처리한다. 전체 구성은 다음과 같다.

| 단계 | 둘 곳 | 1순위 | 대안 | 이유 |
|---|---|---|---|---|
| 청취 시작 | main | 음성 단축키 토글(누르면 듣고 VAD가 끝을 판정), 마스코트 클릭-홀드 | 헬퍼 `CGEventTap`으로 누르는 동안 녹음 | 추가 권한이 없다 |
| 캡처 | 렌더러 | `getUserMedia` + AudioWorklet로 16 kHz mono PCM | 헬퍼 `AVCaptureSession` | 마이크 권한을 Electron 번들 하나로 모은다 |
| 발화 구간 검출 | 렌더러 | `@ricky0123/vad-web`(Silero VAD) | `whisper-cpp-node` 내장 VAD | 렌더러에서 바로 돈다 |
| 인식(STT) | main + Swift 헬퍼 | Apple SpeechTranscriber(ko_KR·ja_JP) | whisper.cpp, sherpa-onnx, `gpt-transcribe`, RTZR | 무료·온디바이스, 어댑터로 교체 |
| 언어 결정 | main | 캐릭터 기본 언어 + 단축키 + KO/JA 재전사 배지 | {ko, ja}로 제한한 자동 감지 | 짧은 발화에서 오인이 없다 |
| 두뇌 | 기존 자식 프로세스 | 잡담 chatd(stream-json), 지시 세션(runner) | — | 지시 전사는 입력창에서 확인 후 전송 |
| 문장 분할 | main | 한·일 구두점과 종결어미 기준 증분 분할기 | ElevenLabs `stream-input` | 첫 청크를 짧게 |
| 합성(TTS) | main | 엔진 어댑터 + 해시 캐시 + 폴백 사슬 | — | API 키는 main에만 둔다 |
| 재생 | 렌더러 | WebAudio, PCM 스트림은 AudioWorklet 링버퍼 | MediaSource(mp3) | 캡처와 같은 렌더러에서 재생 |

무거운 부품의 자리도 미리 정해 둔다. API 키와 네이티브 애드온은 main 프로세스에 두고, Apple 음성 API는 기존 `claudewin`과 같은 방식의 두 번째 Swift 헬퍼(가칭 `sttd`)로 뺀다. 헬퍼 방식은 앱을 재서명할 필요가 없고, 네이티브 애드온의 Electron ABI 문제를 피하며, 헬퍼가 죽어도 오버레이가 살아남는다. Apple 음성 모델은 시스템 저장소에 내려받아 쓰므로 앱 용량과 런타임 메모리를 늘리지 않는다 ([WWDC25 세션 277](https://developer.apple.com/videos/play/wwdc2025/277/)). 반면 로컬 Whisper·sherpa 모델은 압축 기준 수백 MB에서 1 GB 안팎이라 ([sherpa-onnx asr-models](https://github.com/k2-fsa/sherpa-onnx/releases/tag/asr-models)) 16 GB 맥에서 상주 CLI 프로세스들과 메모리를 다툰다. 쓰지 않을 때 내리고, 설치 스크립트가 rsync로 복사하는 앱 폴더 밖에 둔다.

## 듣기는 이미 깔린 Apple 한국어 모델로 시작하고 언어는 사용자가 정한다

### Apple 헬퍼는 무료·온디바이스지만 정확도와 권한이 미지수다

제로셋업 1순위는 macOS 26의 **SpeechAnalyzer와 SpeechTranscriber**다. 메모·음성 메모 앱과 같은 계열의 모델을 온디바이스로 돌리고, 말하는 동안 거친 결과를 먼저 낸 뒤 몇 초에 걸쳐 고쳐 가는 volatile 결과를 지원한다 ([WWDC25 세션 277](https://developer.apple.com/videos/play/wwdc2025/277/)). 출시 때 지원한 10개 언어에 한국어와 일본어가 모두 들었다 ([addpipe: Apple SpeechAnalyzer](https://blog.addpipe.com/apple-speechanalyzer-api/)). 이 Mac에서 probe로 확인한 결과 **ko_KR 자산은 이미 설치돼 있고 ja_JP는 지원되지만 미설치**라 한 번 내려받아야 한다. 동시에 예약할 수 있는 로케일은 5개라 두 언어를 함께 둬도 된다. 구형 SFSpeechRecognizer로 일본어를 부르면 이 Mac에서는 온디바이스 인식이 안 돼 Apple 서버로 간다 ([로컬 실측 기록](<../research/마스코트 음성 대화 도구 조사/japanese_and_bilingual_stt.md>)). 이 구형 API는 오디오 1분 제한까지 있어 ([Apple: SFSpeechRecognizer](https://developer.apple.com/documentation/speech/sfspeechrecognizer)) 새 경로에서 뺀다. 약점은 정확도가 알려지지 않았다는 점이다. **Apple은 한국어·일본어 오류율을 공개하지 않았고**, 공개 비교는 영어 LibriSpeech에서 SpeechAnalyzer의 WER 2.12%가 Whisper Small의 3.74%보다 낫다는 정도다 ([LoroNote](https://loronote.com/en/blog/apple-speechanalyzer-vs-whisper)). 1순위로 두는 이유는 정확도가 아니라 키·모델 배포·비용이 없고 소리가 기기를 떠나지 않는다는 데 있다. 코드를 한 줄도 쓰지 않는 대안도 있다. macOS 시스템 받아쓰기는 한국어와 일본어를 온디바이스로 지원해 지금 입력창에서 바로 말로 입력할 수 있지만 ([Apple macOS Feature Availability](https://www.apple.com/macos/feature-availability/)), 마스코트는 사용자가 말하는 중인지 알 수 없다.

헬퍼 설계의 핵심은 누가 마이크를 여느냐다. 비샌드박스 앱이 헬퍼 안에서 AVAudioEngine으로 녹음하며 SpeechAnalyzer를 돌리자 마이크 권한 창이 10~20번 넘게 반복됐다는 보고가 있고 ([sophiaclaw voice-wake 상태 문서](https://cdn.jsdelivr.net/npm/sophiaclaw@0.2.4/docs/status/voice-wake.md)), AVAudioEngine 탭은 블루투스 장치에서 실패한다는 포럼 사례도 있다 ([Apple Developer Forums #819555](https://developer.apple.com/forums/thread/819555)). 그래서 렌더러가 `getUserMedia`로 잡은 16 kHz PCM을 헬퍼 stdin에 흘리고, 헬퍼는 부분·최종 결과를 JSON 줄로 stdout에 내는 구성이 안전하다. 마이크 권한은 이미 `NSMicrophoneUsageDescription`을 가진 Electron 번들이 받는다 ([로컬 확인: Electron.app Info.plist](file:///Users/dobedub/Desktop/skinclaude/overlay/node_modules/electron/dist/Electron.app/Contents/Info.plist)). 헬퍼는 ko_KR과 ja_JP 인식기를 미리 하나씩 만들어 두고 앱이 고른 쪽으로 PCM을 보낸다. 남는 미지수는 SpeechTranscriber가 별도의 음성인식 권한을 요구하느냐다. 라이브 오디오에는 마이크 권한만 있으면 된다는 분석이 있는 반면 ([Blake Crosley](https://blakecrosley.com/blog/speech-framework-vs-sfspeechrecognizer)), 첫 전사 때 음성인식 권한 창이 떠서 바이너리를 앱 번들로 감싼 사례도 있다 ([simonw/speech-analyzer-cli](https://github.com/simonw/speech-analyzer-cli/blob/main/README.md)). Electron 번들에는 음성인식 사용 설명 키가 없고, 그 Info.plist를 고친 뒤 재서명하지 않으면 TCC가 요청을 조용히 거부한다 ([t3code 이슈 #728](https://github.com/pingdotgg/t3code/issues/728)). 권한이 필요하다고 판명되면 헬퍼를 작은 `.app`으로 감싸는 방식이 대안이다. 구현 전에는 Homebrew의 `yap dictate --locale`로 한·일 인식 품질을 먼저 들어 볼 수 있다 ([finnvoor/yap](https://github.com/finnvoor/yap)). Node-API 애드온 `@xsai-apple-speech/transcription-native`도 있지만 Electron main 프로세스에서만 쓰라는 조건이 붙는다 ([npm @xsai-apple-speech/transcription-native](https://www.npmjs.com/package/@xsai-apple-speech/transcription-native)).

### 언어는 자동 감지보다 캐릭터와 단축키가 정한다

Apple 경로에서는 언어를 앱이 먼저 정해야 한다. SpeechTranscriber는 인스턴스마다 로케일 하나만 받고 자동 언어 식별이 없다 ([Apple: SpeechTranscriber](https://developer.apple.com/documentation/speech/speechtranscriber)). 자동 감지를 붙이는 것은 생각보다 위험하다. 한국어 방송 발화 3,115개에서 Whisper large-v3-turbo의 언어 식별은 **95.2%**를 맞혔지만 ([Solbox LID 비교](https://doc.scenemaker.solbox.com/en/docs/poc/audio-bench/2)), 같은 팀은 12초짜리 한국어가 일본어로 인식된 사례를 보고했다 ([Solbox 블로그](https://doc.scenemaker.solbox.com/en/blog/4)). Whisper는 언어를 잘못 고르면 전사 대신 번역문을 내기도 한다 ([OpenAI Community](https://community.openai.com/t/whisper-3-detects-incorrect-language-translates-instead-of-transcribes/828870)). "네"나 "はい"처럼 1초 안팎인 마스코트 대화에서는 더 불안하다. 그러므로 **기본은 명시적 선택**이다. 캐릭터마다 기본 언어를 두고 단축키로 바꾸며, 전사 결과 옆 KO/JA 배지를 누르면 보관해 둔 마지막 발화를 반대 언어로 다시 전사한다. 자동 모드는 설정에서 켜는 보조 기능으로 둔다. 이때는 whisper.cpp가 주는 언어별 확률 배열에서 ko와 ja만 떼어 비교하고 ([whisper.h](https://github.com/ggml-org/whisper.cpp/blob/master/include/whisper.h)), 한국어 결과의 한글 비율이 30% 미만이면 버리는 Solbox식 사후 검사를 붙인다. Apple의 텍스트 언어 판별기 NLLanguageRecognizer는 한글과 가나를 정확히 가르지만, 한·일이 섞인 문장은 가나가 조금만 있어도 일본어로 뭉갠다 ([로컬 실측 기록](<../research/마스코트 음성 대화 도구 조사/japanese_and_bilingual_stt.md>)). 그래서 사후 검사 규칙은 문자 비율로 짜는 편이 명확하다. 이 설계의 전제는 사용자가 한 캐릭터에게 두 언어를 섞어 쓰느냐다. 캐릭터마다 언어가 정해져 있다면 자동 감지는 아예 필요 없다.

### 로컬 업그레이드는 Whisper 하나냐 언어별 모델이냐의 선택이다

Apple이 한국어 개발 용어나 일본어에서 모자라면 로컬 오픈 모델로 올린다. 가장 단순한 구성은 whisper.cpp(v1.9.4, Metal·Core ML 가속) ([ggml-org/whisper.cpp](https://github.com/ggml-org/whisper.cpp)) 위에 large-v3-turbo 한 모델을 올리고, Silero VAD를 내장한 `whisper-cpp-node`로 부르는 것이다 ([npm whisper-cpp-node](https://www.npmjs.com/package/whisper-cpp-node)). 같은 Swift 헬퍼 안에서 돌리고 싶다면 WhisperKit(MIT, 권장 압축 turbo 모델 626 MB)이 같은 자리에 들어간다 ([argmax-oss-swift](https://github.com/argmaxinc/argmax-oss-swift)). Whisper는 **일본어에 강하고 한국어에 약하다**. large-v3의 일본어 CER은 CommonVoice 8에서 8.5, JSUT에서 7.1이지만 ([kotoba-whisper-v2.0 모델 카드](https://huggingface.co/kotoba-tech/kotoba-whisper-v2.0)), 한국어 대화체 KsponSpeech Eval-Other CER은 11.13%다 ([Edge AI and Vision Alliance](https://www.edge-ai-vision.com/2025/11/small-models-big-heat-conquering-korean-asr-with-low-bit-whisper/)). 언어별 최적 구성은 sherpa-onnx(v1.13.8, Node 애드온 `sherpa-onnx-node`) 런타임 하나에 언어마다 다른 모델을 올리는 방식이다 ([k2-fsa/sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx)). 한국어는 2026년 공개된 **Qwen3-ASR-0.6B**(FLEURS 한국어 오류율 3.72)가, 일본어는 **parakeet-tdt_ctc-0.6b-ja**(JSUT CER 6.4, CC-BY-4.0)가 맡는다 ([Qwen3-ASR 기술 보고서](https://arxiv.org/html/2601.21337), [HF nvidia/parakeet-tdt_ctc-0.6b-ja](https://huggingface.co/nvidia/parakeet-tdt_ctc-0.6b-ja)). Qwen3-ASR-0.6B는 FLEURS 일본어 8.33으로 약하므로 일본어에는 쓰지 않는다. int8 자산은 각각 879 MB와 489 MB다 ([sherpa-onnx asr-models](https://github.com/k2-fsa/sherpa-onnx/releases/tag/asr-models)). 가장 가벼운 선택은 한·일을 한 모델로 받고 언어 태그까지 주는 SenseVoice-Small(int8 166 MB, CommonVoice CER 한국어 8.28·일본어 11.96)이다 ([SenseVoice 논문](https://arxiv.org/html/2407.04051)). 이 수치들은 데이터셋과 지표가 달라 서로 직접 비교할 수 없다. 네이티브 애드온은 N-API 기반이면 ABI 문제가 적지만, Electron 44(Node 22)에서 로드 시험은 거쳐야 한다(공식 확인 없음). 스트리밍 모델은 필요 없다. 누르고 말하는 턴제라 VAD로 끊은 발화를 한 번에 인식하면 충분하고, 한·일 모두 쓸 만한 로컬 스트리밍 모델 짝도 없다.

### 클라우드는 한·일을 한 요청에서 가르는 곳이 편하다

클라우드로 가면 한 요청 안에서 한·일을 가려 주는 서비스가 연동을 줄인다. **OpenAI `gpt-transcribe`**는 분당 $0.0045에 `languages` 배열로 후보 언어를 여러 개 받고, 감지한 언어를 전사와 함께 JSON으로 돌려주며, `keywords`로 "클로드 코드"나 파일명 같은 용어를 보정한다 ([OpenAI API pricing](https://developers.openai.com/api/docs/pricing), [OpenAI STT 가이드](https://developers.openai.com/api/docs/guides/speech-to-text)). 신형 모델의 한·일 수치는 없고, 구형 GPT-4o mini Transcribe의 FLEURS 일본어 CER은 9.89로 Whisper(4.97)보다 나빴다 ([Voxtral Realtime 논문](https://arxiv.org/html/2602.11298)). 한국어 품질을 앞세우면 **리턴제로 RTZR**이다. 기본 모델 sommers가 한국어와 일본어를 모두 받고, 스트리밍에는 언어별 모델이 따로 있으며, 처음 10시간이 무료이고 이후 시간당 ₩1,000이다 ([RTZR 파일 STT](https://developers.rtzr.ai/docs/stt-file/), [RTZR 스트리밍 STT](https://developers.rtzr.ai/docs/stt-streaming/), [RTZR pricing](https://rtzr.ai/pricing)). 리턴제로 벤치마크의 평균 CER은 5.91로 OpenAI Whisper(11.39)를 크게 앞서지만, 리턴제로가 만든 표다 ([rtzr/Awesome-Korean-Speech-Recognition](https://github.com/rtzr/Awesome-Korean-Speech-Recognition)). 최저가는 분당 $0.003인 **Voxtral Mini Transcribe V2**다. Mistral이 잰 FLEURS 일본어 CER 4.14가 같은 표에서 가장 좋지만 자동 언어 감지 기능은 확인되지 않았다 ([Mistral: Voxtral Transcribe 2](https://mistral.ai/news/voxtral-transcribe-2)). 피할 곳도 있다. Deepgram의 코드스위칭 `multi` 모드에는 일본어는 있고 한국어는 없다 ([Deepgram 모델·언어](https://developers.deepgram.com/docs/models-languages-overview)). AssemblyAI 실시간은 한국어를 지원하지 않는다 ([AssemblyAI Korean](https://www.assemblyai.com/languages/korean)). Gemini 3.5 Transcribe 무료 티어는 입력을 제품 개선에 쓴다 ([Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing)). Soniox는 한국 페이지의 한국어 CER 표와 일본 페이지의 일본어 오류율 표 숫자가 똑같아 언어별 측정값으로 믿기 어렵다 ([Soniox Korea](https://soniox.com/korea), [Soniox Japan](https://soniox.com/japan)). 비용은 결정 요인이 아니다. 하루 10분씩 말하면 `gpt-transcribe`로도 월 $1.4 안팎이다.

전사 결과를 어디로 보낼지도 정해야 한다. 지시 모드에서는 전사 오류가 곧 잘못된 작업 지시가 되므로 결과를 입력창에 채워 사용자가 확인한 뒤 보내게 하고, 잡담만 바로 보낸다. 일본어로 말을 걸면 캐릭터도 일본어로 답하도록 페르소나 지시에 응답 언어 규칙을 더한다.

| 경로 | 한국어 근거 | 일본어 근거 | 언어 결정 | 비용·크기 | 역할 |
|---|---|---|---|---|---|
| Apple SpeechTranscriber(Swift 헬퍼) | 공개 수치 없음(ko_KR 설치됨) | 공개 수치 없음(ja_JP 1회 다운로드) | 로케일 지정, 자동 감지 없음 | 무료, 앱 용량 증가 없음 | 1단계 기본 |
| whisper.cpp large-v3-turbo | large-v3 KsponSpeech CER 11.13 | large-v3 JSUT CER 7.1 | ko·ja 확률만 비교 | 무료, 압축 모델 약 0.6 GB | 모델 하나로 끝내는 로컬 |
| sherpa-onnx: Qwen3-ASR-0.6B + parakeet-ja | FLEURS 3.72 | JSUT CER 6.4 | 앞단 언어 결정 필요 | 무료, int8 약 1.4 GB | 언어별 최적 로컬 |

| RTZR | 자체 벤치 CER 5.91 | 업체 주장뿐 | 모델로 지정, 파일 API는 감지 | 10시간 무료, ₩1,000/시간 | 한국어 품질 우선 |

수치는 데이터셋과 지표(CER·WER)가 달라 행끼리 비교할 수 없다. 이 앱의 실제 조건인 짧은 명령, 개발 용어가 섞인 구어, 맥 내장 마이크에서 잰 비교는 어디에도 없다.

## 목소리는 '한 사람이 두 언어'냐 '일본어 애니풍'이냐에서 갈린다

TTS를 고르는 핵심 질문은 품질 순위가 아니라 두 요구 중 무엇을 앞세우느냐다. 하나는 같은 캐릭터가 한국어와 일본어를 **같은 목소리**로 말하는 것이고, 다른 하나는 일본어 대사가 **애니풍으로 귀엽게** 들리는 것이다. 다국어 클라우드 엔진은 한 보이스로 두 언어를 말하게 하지만 원래 억양이 따라온다. ElevenLabs는 다국어 합성에서 화자의 원래 억양까지 유지된다고 밝혔고 ([ElevenLabs 블로그: Multilingual v2](https://elevenlabs.io/blog/elevenlabs-comes-out-of-beta-and-releases-eleven-multilingual-v2-a-foundational-ai-speech-model-for-nearly-30-languages)), Qwen3-TTS는 프리셋 화자가 10개 언어를 모두 말하지만 모국어로 쓰라고 권하며 ([Qwen3-TTS README](https://github.com/QwenLM/Qwen3-TTS)), OpenAI TTS에는 일본어에서 미국식 억양이 강하고 부드럽고 귀여운 여성 목소리를 찾기 어렵다는 사용자 지적이 있다 ([OpenAI Community](https://community.openai.com/t/how-to-get-a-soft-and-cute-female-voice-with-openai-tts/1363873)). 반대로 VOICEVOX·AivisSpeech 같은 일본어 전용 엔진은 애니풍 캐릭터와 스타일이 풍부하지만 한국어를 못 한다. 두 언어를 같은 목소리로 네이티브처럼 말하는지 검증한 독립 자료는 없고, 종합 순위인 Artificial Analysis의 Elo도 언어를 나누지 않는다 ([Artificial Analysis TTS 리더보드](https://artificialanalysis.ai/text-to-speech/leaderboard)).

### Gemini 프리셋이 두 언어를 가장 싸게 한 목소리로 묶는다

기본값은 **Gemini 3.8 Flash TTS**다. 2026-09-22에 GA가 됐고 ([Gemini 3.8 Flash TTS 모델 페이지](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash-tts)), 한국어를 지원하며 입력 언어를 자동으로 감지한다. 30개 프리셋 보이스에 턴마다 자연어 스타일(`speech_metadata.style`)과 `<sigh>` 같은 발성 이벤트를 붙이고, 한 요청에 두 화자까지 합성하며, 스트리밍하면 헤더 없는 24 kHz PCM이 나온다 ([Gemini API: Speech generation](https://ai.google.dev/gemini-api/docs/speech-generation)). Cloud TTS 문서는 Gemini-TTS에서 ja-JP와 ko-KR을 GA로 표기하고 보이스 이름을 언어와 무관하게 쓴다 ([Cloud TTS: Gemini-TTS](https://docs.cloud.google.com/text-to-speech/docs/gemini-tts)). 한 보이스 이름을 두 언어에 그대로 쓰면 "한 목소리 두 언어"를 가장 싸게 얻는다는 뜻이다. 공식 설명어로 고르면 초텐은 Leda(Youthful)·Zephyr(Bright)·Autonoe(Bright), 아메는 Achernar(Soft)·Vindemiatrix(Gentle)·Kore(Firm)가 출발점이다. 두 화자 합성을 쓰면 초텐과 아메가 주고받는 대사를 한 요청으로 만들 수 있다. 3.8부터는 설명문으로 영구 보이스 ID(1년 유지, 프로젝트당 200개)를 설계할 수 있지만, 설계 보이스가 여러 언어를 말하는지는 문서에 없다 ([Gemini API: Voice design](https://ai.google.dev/gemini-api/docs/voice-design)). 오디오 출력은 1M 토큰당 Flash $9, Flash-Lite $6(초당 25토큰)이고 **2027-01-01부터 두 배**가 된다 ([Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing)). 무료 티어의 입출력은 제품 개선과 사람 검토 대상이므로 ([Gemini API terms](https://ai.google.dev/gemini-api/terms)) 작업 내용이 섞이는 대사는 유료 티어로 보낸다. 모든 출력에는 SynthID 워터마크가 들어간다 ([Google 블로그: Gemini 3.8 TTS](https://blog.google/innovation-and-ai/models-and-research/gemini-models/gemini-3-8-text-to-speech/)). Artificial Analysis Elo는 1268로 3위다. 약점은 비모국어 쪽 억양과 공식 첫 음성 지연 수치가 확인되지 않았다는 점이다.

### ElevenLabs 설계와 리믹스가 '같은 사람'에 가장 가깝다

목소리 동일성과 연기 품질을 더 원하면 **ElevenLabs**로 올린다. 2026-09-28에 나온 Eleven v4가 Elo 1316으로 1위다 ([ElevenLabs Changelog](https://elevenlabs.io/docs/changelog), [Artificial Analysis](https://artificialanalysis.ai/text-to-speech/leaderboard)). 두 기능의 조합이 핵심이다. Voice Design은 설명문으로 새 보이스를 만들고, `seed`를 고정하면 같은 입력에서 같은 보이스가 나온다 ([ElevenLabs API: Design a voice](https://elevenlabs.io/docs/api-reference/text-to-voice/design)). 설명문에는 품질 문구와 나이·억양·성별·톤·속도를 넣으라고 권한다 ([ElevenLabs 블로그: Voice Design v3](https://elevenlabs.io/blog/voice-design-v3)). Voice Remix는 설계 보이스의 정체성을 중간 강도로 지키면서 억양만 바꿀 수 있다 ([ElevenLabs: Voice remixing](https://elevenlabs.io/docs/overview/capabilities/voice-remixing)). 캐릭터마다 억양이 중립인 20대 초반 여성 베이스를 설계한 뒤 일본어 네이티브 억양판과 서울 한국어 억양판으로 리믹스하면, voice_id 네 개로 "같은 사람이 두 언어를 말하는" 구성에 가장 가까워진다. 다만 한·일 억양 리믹스의 품질 평가는 아직 없다. 합성 모델도 골라야 한다. v4 문서는 설계 보이스가 v4에서 이전 모델보다 덜 연기적일 수 있다고 적었다 ([ElevenLabs: Eleven v4](https://elevenlabs.io/docs/overview/capabilities/text-to-speech/eleven-v4)). 그래서 초텐의 `[excited]`, 아메의 `[sighs]`와 말줄임표 같은 오디오 태그 연기는 v3로 하고, v4는 청취 비교에만 넣는다 ([ElevenLabs v3 prompting](https://elevenlabs.io/docs/best-practices/prompting/eleven-v3)). 단가는 1천 자당 v3·v4 $0.08, Flash v2.5·v4 Turbo $0.04다 ([ElevenLabs API pricing](https://elevenlabs.io/pricing/api)). 무료 플랜은 월 1만 크레딧이라 시험용에 그치고, 두 요금 페이지의 플랜 포함량 표기가 서로 달라 실제 청구액은 가입할 플랜에 따라 달라진다 ([ElevenLabs Pricing](https://elevenlabs.io/pricing)).

### 일본어 애니풍은 무료 로컬 VOICEVOX가 맡는다

일본어 애니풍이 먼저라면 일본어만 **VOICEVOX**(0.25.2, Apple Silicon 빌드)에 맡긴다 ([VOICEVOX Releases](https://github.com/VOICEVOX/voicevox/releases)). 로컬 HTTP 엔진(포트 50021)에 쿼리 생성과 합성을 차례로 요청하고 `speedScale`·`pitchScale`·`intonationScale`로 톤을 다듬는다 ([voicevox_engine](https://github.com/VOICEVOX/voicevox_engine)). 초텐은 속도와 억양 폭을 올리고, 아메는 속도를 늦추고 억양을 평탄하게 누르는 식이다. AivisSpeech는 같은 형태의 API를 포트 10101에서 내므로 클라이언트 코드를 그대로 쓴다 ([AivisSpeech-Engine](https://github.com/Aivis-Project/AivisSpeech-Engine)). 스타일로 고르면 초텐은 春日部つむぎ(공식 설명 "元気で明るい")와 満別花丸의 元気·ぶりっ子, 아메는 冥鳴ひまり, ぞん子의 低血圧, あんこもん의 けだるげ가 후보다 ([VOICEVOX 제품 페이지: 春日部つむぎ](https://voicevox.hiroshiba.jp/product/kasukabe_tsumugi/), [voicevox_vvm](https://github.com/VOICEVOX/voicevox_vvm)). 夜語トバリ는 明るい와 呆れ를 한 화자 안에 모두 가졌으므로, 두 캐릭터를 같은 사람의 두 얼굴처럼 들리게 하고 싶을 때 쓸 수 있다. 라이선스는 **冥鳴ひまり가 기존 IP 캐릭터의 목소리로 쓰는 것을 명시적으로 허용**해 아메에 가장 깔끔하다 ([冥鳴ひまり 이용규약](https://www.meimeihimari.com/terms-of-use)). VOICEVOX는 상업·비상업 모두 허용하지만 "VOICEVOX:캐릭터명" 크레딧을 요구하므로 앱 정보 화면에 넣는다 ([VOICEVOX 이용규약](https://voicevox.hiroshiba.jp/term/)). AivisHub 모델(ACML)은 크레딧 의무가 없고, 원 화자나 공식 관계자로 오인시키는 이용만 금지한다 ([ACML 1.0](https://raw.githubusercontent.com/Aivis-Project/ACML/master/ACML-1.0.md)). 2026년 공개된 Irodori-TTS(MIT)는 일본어 설명문만으로 목소리를 설계하지만, 일본어 전용이고 한자 읽기가 약하다고 모델 카드가 스스로 밝힌다 ([HF Irodori-TTS-500M-v3](https://huggingface.co/Aratako/Irodori-TTS-500M-v3)). 대가는 언어마다 목소리가 달라진다는 점이고, 한국어를 Gemini Flash-Lite로 받치면 월 약 $5로 가장 싸다. 성인 톤도 챙긴다. 春日部つむぎ와 四国めたん은 설정상 고교생이므로 "20대 초반" 인상이 필요하면 설정상 성인인 캐릭터를 앞세우고 ([VOICEVOX 제품 페이지: 四国めたん](https://voicevox.hiroshiba.jp/product/shikoku_metan/)), 櫻歌ミコ의 ロリ처럼 아동을 지향하는 스타일은 뺀다.

### 완전 오프라인은 Qwen3-TTS, 최후 폴백은 macOS say다

완전 오프라인의 1순위는 **Qwen3-TTS**(Apache-2.0)다. 한·일을 포함한 10개 언어를 말하고, 장난스럽고 가벼운 음색의 일본어 모국어 프리셋 Ono_Anna와 한국어 모국어 프리셋 Sohee, 설명문으로 음색을 만드는 VoiceDesign을 갖췄다 ([Qwen3-TTS](https://github.com/QwenLM/Qwen3-TTS)). mlx-audio가 이를 Apple Silicon에서 돌리고 OpenAI 호환 `/v1/audio/speech` 서버를 띄우므로, 클라우드와 같은 클라이언트 코드로 부를 수 있다 ([mlx-audio](https://github.com/Blaizzy/mlx-audio)). 걸림돌은 속도다. 1.7B 4비트가 M5 Pro에서 RTF 0.79였고 ([soniqo 벤치마크](https://soniqo.audio/benchmarks)), PyTorch MPS로는 M3 Max에서 RTF 2.97로 실시간보다 세 배 느렸다 ([tinycomputers](https://tinycomputers.io/posts/the-real-cost-of-running-qwen-tts-locally-three-machines-compared.html)). M4 실측은 없다. 고정 대사는 미리 렌더링하고, 실시간 답은 문장 단위로 겹쳐 돌려야 한다. VoiceDesign은 호출마다 목소리가 조금씩 흔들리므로, 설계로 만든 짧은 레퍼런스를 Base 모델의 복제 프롬프트로 고정하는 절차가 권장된다(문서 미러의 검색 요약) ([Qwen3-TTS voice cloning 가이드](https://mintlify.com/QwenLM/Qwen3-TTS/guides/voice-cloning)). 이 레퍼런스는 직접 설계한 합성 음성이지 실존 인물의 녹음이 아니다. 대안인 CosyVoice 3(0.5B, 한·일 포함 9개 언어, 감정 지시)은 같은 벤치에서 RTF 0.59로 더 빨랐지만 Mac 설치 난이도는 확인되지 않았다 ([FunAudioLLM/CosyVoice](https://github.com/FunAudioLLM/CosyVoice), [soniqo 벤치마크](https://soniqo.audio/benchmarks)). 마지막 폴백인 macOS `say`는 이 Mac에 설치된 한국어 음성이 super-compact 품질의 Yuna와 장난감 같은 Eloquence 음성뿐이라 ([로컬 확인 기록](<../research/마스코트 음성 대화 도구 조사/text_to_speech.md>)) 네트워크가 끊겼을 때의 비상용이다.

캐릭터별 후보를 정리하면 다음과 같다. 보이스는 이름과 공식 설명어로 고른 출발점이며, 확정은 청취 시험 뒤에 한다.

| 안 | 초텐(밝고 발랄한 아이돌) | 아메(건조하고 나른한 츤데레) | 두 언어 같은 목소리 | 월 비용 추정* | 주의 |
|---|---|---|---|---|---|
| A. Gemini 3.8 Flash TTS | Leda(Youthful)·Zephyr(Bright)·Autonoe(Bright) + 스타일 "20대 초반, 들뜨고 달콤한 아이돌 스트리머, 빠르고 통통 튀게" | Achernar(Soft)·Vindemiatrix(Gentle)·Kore(Firm) + 스타일 "조용하고 무표정, 건조하고 나른한 20대 초반, 가끔 작은 한숨" | 된다(보이스 이름이 언어 공통) | 약 $13, Flash-Lite 약 $9, 2027년 두 배 | 비모국어 억양 미검증, 무료 티어는 데이터 활용 |
| B. ElevenLabs 설계 + 리믹스 | 설계문 "20대 초반 여성, 밝고 달콤한 고음, 빠르고 노래하듯, 웃음 띤" + `[excited]` | 설계문 "20대 초반 여성, 부드럽고 약간 허스키한 중저음, 무심하고 졸린, 건조한 놀림" + `[sighs]` | 된다(캐릭터당 ja·ko 억양판 2개) | v3·v4 약 $31, Flash·v4 Turbo 약 $15 | 리믹스 억양 품질 미검증, v4는 설계 보이스 연기가 약할 수 있음 |

### 2026년에 문을 닫은 곳과 연기가 약한 곳은 거른다

나머지 후보는 걸러진다. 한국 벤더 Supertone은 2026-08-31에 Play와 API를 닫았고 ([Supertone 종료 안내](https://www.supertone.ai/ko/sunset)), 온디바이스 오픈 웨이트 Supertonic도 아카이브돼 업데이트가 끝났다 ([Supertonic README](https://raw.githubusercontent.com/supertone-inc/supertonic/main/README.md)). 일본의 にじボイス는 성우 단체가 캐릭터 목소리가 회원 목소리와 흡사하다고 문제 삼자, 법적 침해는 인정되지 않았다면서도 2026-02-04에 API까지 종료했다 ([PC Watch](https://pc.watch.impress.co.jp/docs/news/2065958.html)). Google Chirp 3 HD는 한·일을 지원하지만 감정·스타일 지시가 없다 ([Chirp 3 HD 문서](https://docs.cloud.google.com/text-to-speech/docs/chirp3-hd)). Azure는 ko-KR과 ja-JP에 여성 다국어 보이스가 없어 언어마다 다른 목소리를 골라야 한다 ([Azure 언어 지원](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/language-support?tabs=tts)). 한국어 MAI-Voice-2 여성 보이스는 excited·joyful 등 13개 스타일로 초텐에 어울리지만, 아직 프리뷰이고 문서마다 이름이 다르다 ([Microsoft Learn: MAI-Voice](https://learn.microsoft.com/azure/ai-services/speech-service/mai-voices)). Elo 2위 Cartesia Sonic 3.6은 한국어를 지원하지만 이 사용량이면 플랜 구조상 월 $49가 든다 ([Cartesia pricing](https://cartesia.ai/pricing)). Typecast는 일본어를 고르면 모든 캐릭터가 네이티브 억양으로 말한다고 주장하지만 벤더 주장이고 ([Typecast Japanese TTS](https://typecast.ai/languages/japanese-text-to-speech/)), 월 20만 크레딧(Lite $15)을 넘으면 Plus $280으로 뛴다 ([Typecast API](https://typecast.ai/developers/api/)). MiniMax에는 Korean_SweetGirl 같은 이름의 보이스가 있지만 성별·나이 정보가 없고, 일본어 쪽에는 발랄한 젊은 여성 보이스가 드물다 ([MiniMax system voice ID](https://platform.minimax.io/docs/faq/system-voice-id)). Fish Audio는 UTF-8 바이트로 과금해 한글·가나가 불리하다 ([Fish Audio pricing](https://docs.fish.audio/developer-guide/models-pricing/pricing-and-rate-limits)).

### 연기와 일관성은 엔진이 아니라 앱이 쥔다

어느 엔진을 고르든 연기는 앱이 쥔다. 앱의 기존 감정 태그를 엔진 중립 중간 표현(감정, 강도, 캐릭터 기본 톤)으로 두고 엔진별 어댑터가 번역한다. 엔진마다 제어 방식이 다르기 때문이다. ElevenLabs v3는 대괄호 오디오 태그, Gemini 3.8은 스타일 문장과 꺾쇠 이벤트, OpenAI와 Qwen3는 자연어 지시, Azure MAI는 SSML `style`과 `styledegree`, VOICEVOX는 스타일 ID와 스케일 값을 쓴다 ([ElevenLabs v3 prompting](https://elevenlabs.io/docs/best-practices/prompting/eleven-v3), [Gemini API: Speech generation](https://ai.google.dev/gemini-api/docs/speech-generation), [Microsoft Learn: MAI-Voice](https://learn.microsoft.com/azure/ai-services/speech-service/mai-voices)). 같은 기쁨이라도 초텐은 강도를 올리고 아메는 내리는 캐릭터 보정을 어댑터가 맡는다. 태그나 "…"를 쓰는 엔진에서는 말풍선용 텍스트와 발화용 텍스트를 나눠 태그가 화면에 보이지 않게 한다. 대사의 언어는 한글과 가나의 비율로 판별해 엔진이나 voice_id를 고른다. 일관성은 보이스 ID·프리셋 이름·모델 스냅샷 고정, 캐릭터별 기본 연기 지시문 상수화, 설계 프롬프트와 seed 보관, 그리고 (엔진, 보이스, 지시문, 텍스트) 해시를 키로 한 오디오 캐시로 지킨다. 캐시는 되풀이되는 대사를 같은 소리로 재생하고, 그 줄의 비용과 지연을 없앤다.

### 실존 성우를 닮게 만드는 일은 금지선이다

금지선은 분명하다. 2026년 4월 TV 애니메이션이 방영을 시작해 초텐에게 공식 성우가 생겼다 ([crank-in: 2026 봄 애니](https://www.crank-in.net/animation/spring2026/1963)). 실존 성우의 목소리를 복제하거나 닮게 조정하는 일, 설계 프롬프트에 성우 이름을 넣는 일, 인터넷에 도는 캐릭터 음성 모델을 받아 쓰는 일은 하지 않는다. ElevenLabs는 동의 없는 실존 인물 음성 복제를 금지하고 ([ElevenLabs Help: No-Go Voices](https://help.elevenlabs.io/hc/en-us/articles/22584327690897)), OpenAI는 최종 사용자에게 AI 음성임을 알리라고 요구한다 ([OpenAI TTS 가이드](https://developers.openai.com/api/docs/guides/text-to-speech)). VOICEVOX 음성을 레퍼런스로 다국어 모델에 복제해 "같은 목소리의 한국어판"을 만드는 우회도 쓰지 않는다. 春日部つむぎ처럼 VTuber 목소리를 바탕으로 만든 캐릭터가 있어 결국 실존 인물 복제가 되고 ([crystal-method: VOICEVOX 상용 이용](https://crystal-method.com/blog/voicevox-commercial/)), COEIROINK는 규약에서 머신러닝 학습 데이터 사용을 명시적으로 금지한다 ([COEIROINK 이용규약](https://coeiroink.com/terms)). "같은 목소리의 두 언어"는 반드시 텍스트 설계나 프리셋에서 출발한다. 원작은 2022년 발매 때 스토어 링크를 조건으로 2차 창작을 폭넓게 허용했지만 AI 음성 조항은 확인되지 않았다 ([電ファミニコゲーマー](https://news.denfaminicogamer.jp/news/220121b)). 개인 PC 안에서만 재생하면 위험은 낮고, 화면 녹화 등으로 공개할 때는 "AI 합성 음성·팬 제작"을 표기한다. 설계 프롬프트에는 "20대 초반 성인 여성"을 명시해 아동 톤을 막는다.

## 엔진보다 마이크 권한과 스피커 에코가 먼저 발목을 잡는다

가장 먼저 부딪힐 곳은 마이크 권한이다. 지금 오버레이는 LaunchAgent가 bash 스크립트를 실행하고, 스크립트가 `nohup`으로 npm에서 받은 기본 Electron 바이너리를 직접 띄운다 ([로컬 확인: overlay-ctl.sh](file:///Users/dobedub/.skinclaude/overlay-ctl.sh), [로컬 확인: LaunchAgent plist](file:///Users/dobedub/Library/LaunchAgents/com.dobedub.skinclaude.watch.plist)). 그 번들의 ID는 `com.github.Electron`이고 팀 ID가 없는 ad-hoc 서명이다 ([로컬 확인: Electron.app Info.plist](file:///Users/dobedub/.skinclaude/app/node_modules/electron/dist/Electron.app/Contents/Info.plist)). macOS는 권한을 요청한 코드의 책임 주체를 따지는데, Apple DTS는 스크립트가 끼면 시스템이 그 정체를 추적할 좋은 방법이 없다고 설명한다. launchd가 bash를 실행한 사례에서는 권한 창이 아예 뜨지 않았고, 스크립트를 앱으로 감싸서야 풀렸다. 로컬 네트워크 권한 사례지만 같은 개념이 쓰인다 ([Apple Developer Forums #769918](https://developer.apple.com/forums/thread/769918)). Claude Code 문서도 `/voice`의 마이크 권한 창이 터미널 이름으로 뜬다고 적어, 자식 프로세스의 권한이 부모 앱에 귀속됨을 보여 준다 ([Claude Code Docs: Voice dictation](https://code.claude.com/docs/en/voice-dictation)). 게다가 ad-hoc 서명에는 안정적인 지정 요구사항(designated requirement)이 없어, Electron을 업데이트하거나 다시 빌드하면 macOS가 새 바이너리를 같은 앱으로 보지 않고 권한이 사라질 수 있다 ([Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements), [Apple Developer Forums #795739](https://developer.apple.com/forums/thread/795739)). 대응은 확인부터다. `systemPreferences.getMediaAccessStatus`로 상태를 보고 `askForMediaAccess('microphone')`를 부른 뒤, 시스템 설정의 마이크 목록에 어떤 이름이 올라오는지 본다. 한 번 거부되면 다시 묻지 않고, 설정에서 바꾼 뒤에는 재시작해야 한다 ([Electron systemPreferences](https://www.electronjs.org/docs/latest/api/system-preferences)). 귀속이 틀어졌다면 `open`으로 LaunchServices를 거쳐 띄워 보고(추정), 그래도 안 되면 고유 번들 ID와 일관된 자체 서명 인증서를 가진 전용 `.app`으로 포장한다. Electron은 별도 핸들러가 없으면 렌더러의 권한 요청을 자동 승인하므로 ([Electron Security](https://www.electronjs.org/docs/latest/tutorial/security)) 넘을 관문은 macOS TCC 하나다.

청취는 **토글형 푸시투토크**로 시작한다. Electron `globalShortcut`은 키를 누를 때만 콜백을 부르고 뗄 때의 이벤트가 없다 ([Electron globalShortcut](https://www.electronjs.org/docs/latest/api/global-shortcut)). 그래서 단축키를 한 번 누르면 마스코트가 듣는 표정으로 바뀌고, VAD가 침묵을 감지하면 자동으로 끝나며, 다시 누르면 취소되는 방식이 추가 권한 없이 가장 쉽다. 침묵 판정은 Claude Code 내장 받아쓰기의 1,000 ms나 Gemini Live 기본값 약 800 ms에서 출발한다 ([Gemini Live API capabilities](https://ai.google.dev/gemini-api/docs/live-api/capabilities)). 말 중간의 쉼에서 자주 끊기면 한국어를 포함한 23개 언어를 지원한다는 Pipecat의 Smart Turn v3 턴 감지 모델을 더할 수 있다(검색 요약) ([GitHub pipecat-ai/smart-turn](https://github.com/pipecat-ai/smart-turn)). 마스코트를 마우스로 누르고 있는 동안 녹음하는 방식도 창 자체 이벤트라 권한이 필요 없다. VAD는 MIT 라이선스의 Silero VAD v6.2.3이 30 ms 청크를 CPU 스레드 하나로 1 ms 안에 처리하고 ([snakers4/silero-vad](https://github.com/snakers4/silero-vad)), `@ricky0123/vad-web`이 이를 렌더러에서 권한 요청부터 발화 구간 콜백까지 감싸 준다 ([GitHub ricky0123/vad](https://github.com/ricky0123/vad)). 진짜 전역 "누르는 동안 녹음"이 꼭 필요하면 기존 Swift 헬퍼에 `CGEventTap`을 더한다. macOS 26에서는 `NSEvent` 전역 모니터가 크래시한다는 보고가 있기 때문이다 ([Apple Developer Forums #819555](https://developer.apple.com/forums/thread/819555)). 이때는 입력 모니터링 권한과 앞의 귀속 문제를 함께 풀어야 한다. "초텐아" 같은 상시 호출어는 지금 무료 선택지가 없다. Picovoice Porcupine은 한국어를 지원하지만 무료 AccessKey가 2026-06-30에 끊겼고 ([Home Assistant 커뮤니티](https://community.home-assistant.io/t/fyi-picovoice-confirmed-free-tier-accesskeys-will-stop-working-after-june-30-2026/1012744), [Picovoice/porcupine](https://github.com/Picovoice/porcupine)), openWakeWord는 영어 모델뿐이며 ([dscripka/openWakeWord](https://github.com/dscripka/openWakeWord)), sherpa-onnx 키워드 검출에도 한국어 모델이 없다 ([sherpa-onnx kws-models](https://github.com/k2-fsa/sherpa-onnx/releases/tag/kws-models)).

헤드폰 없는 Mac 스피커에서는 마스코트가 제 목소리를 사용자 발화로 알아들을 수 있다. Chromium의 에코 제거가 앱 자신의 재생음을 참조 신호로 쓰는지는 확인되지 않았다. MDN은 `echoCancellation: true`가 최소한 원격 피어 오디오를 지우는 수준이고, 시스템이 내는 소리 전체를 지우는 `"all"` 수준은 시도 대상일 뿐이라고 설명한다 ([MDN: echoCancellation](https://developer.mozilla.org/en-US/docs/Web/API/MediaTrackConstraints/echoCancellation)). 2019년 W3C 논의에서는 Chrome이 WebRTC 원격 피어의 소리만 에코 제거에 고려한다는 지적이 나왔다 ([W3C public-webrtc-logs](https://lists.w3.org/Archives/Public/public-webrtc-logs/2019May/0149.html)). 그 뒤 Chrome 전역 에코 제거가 들어왔다는 요약이 있지만 원문은 확인하지 못했다 ([Chromium issue 40871060](https://issues.chromium.org/issues/40871060)). 그러므로 1단계는 **반이중**이다. 마스코트가 말하는 동안과 끝난 직후 잠깐은 인식 결과를 버리고, 사용자는 단축키나 마스코트 클릭으로 끼어든다. TTS는 마이크를 잡는 렌더러에서 WebAudio로 재생해, 나중에 에코 제거를 시험할 여지를 남긴다. 별도 프로세스인 `say`의 소리는 브라우저 에코 제거의 참조에 들어가지 않을 가능성이 크다(추론). 반이중이 답답해지면 Swift 헬퍼에서 AVAudioEngine 보이스 프로세싱(VPIO)으로 캡처하는 길이 있고, macOS 14부터는 다른 앱 소리를 낮추는 더킹 수준도 조절할 수 있다 ([Apple: voiceProcessingOtherAudioDuckingConfiguration](https://developer.apple.com/documentation/avfaudio/avaudioinputnode/voiceprocessingotheraudioduckingconfiguration)). 다만 이 경로는 헬퍼 녹음의 권한 창 반복 문제를 다시 불러온다.

끼어들기와 발화 순서도 앱이 정한다. 사용자가 말을 시작하면 재생을 즉시 멈추고 TTS 큐를 비운 뒤, Claude가 아직 이전 답을 쓰는 중이면 상주 프로세스에 인터럽트를 보낸다. Claude Code 문서에 따르면 `claude -p`는 SIGTERM을 받으면 코드 143으로 끝나며 진행 중인 턴을 결과 없이 남긴다. 턴만 끝내려면 SIGINT나 Agent SDK의 `interrupt()`를 써야 한다 ([Claude Code Docs: Run programmatically](https://code.claude.com/docs/en/headless)). 두 캐릭터와 여러 작업 세션의 나레이션은 전역 오디오 큐 하나를 공유하는 턴제로 돌려 동시에 말하지 않게 하고, 큐 항목에 수명을 둬 오래된 대사가 뒤늦게 나오지 않게 한다. 투명 창이 가려지거나 비활성일 때 VAD 프레임과 재생 타이머가 느려지지 않도록 `backgroundThrottling`(기본 true)을 끄고, 자동 재생은 기본 정책이 사용자 제스처를 요구하지 않으므로 그대로 둔다 ([Electron WebPreferences](https://www.electronjs.org/docs/latest/api/structures/web-preferences)).

## 무료 뼈대 위에서 두 번의 시험으로 엔진을 확정한다

첫 단계는 무료 부품으로 뼈대를 세우고 엔진을 어댑터 뒤로 숨기는 일이다. 렌더러 캡처, VAD, IPC, Swift 헬퍼의 stdin/stdout 규약을 먼저 만들고, STT는 Apple SpeechTranscriber(ko_KR 설치본에 ja_JP 1회 다운로드), 청취는 토글과 반이중으로 시작한다. TTS는 Gemini 3.8 Flash TTS의 프리셋 보이스에 캐릭터별 고정 스타일 문장을 붙이고, 네트워크가 끊기면 한국어는 `say`, 일본어는 VOICEVOX를 깔아 둔 경우 그쪽으로 떨어지게 한다. 터치 반응과 작업 알림처럼 되풀이되는 고정 대사는 설치 때 한·일 × 캐릭터 × 감정 변형으로 미리 렌더링해 둔다. 그러면 과금과 지연이 Claude가 새로 쓴 문장에만 남는다. 개발 중 시험 대사는 Gemini 무료 티어로 돌려도 되지만, 작업 내용이 섞이는 실사용은 유료 티어로 옮긴다.

두 번째 단계는 두 번의 시험이다. 받아쓰기 시험은 맥 내장 마이크로 녹음한 한국어·일본어 짧은 명령과 잡담을 50개씩 준비해 Apple, whisper.cpp turbo, sherpa-onnx의 Qwen3-ASR·parakeet-ja·SenseVoice에 넣고, 원하면 `gpt-transcribe`·Voxtral·RTZR도 더한다. 재는 것은 오류율, 첫 결과까지의 지연, 자동 모드를 쓸 경우의 언어 판정 정답률이다. 한국어는 "커피 한 잔"과 "커피 한잔"처럼 띄어쓰기만 달라도 WER이 50%가 되므로 CER로 잰다 ([rtzr/Awesome-Korean-Speech-Recognition](https://github.com/rtzr/Awesome-Korean-Speech-Recognition)). 청취 시험은 캐릭터마다 인사·기쁨·삐짐·졸림·놀람·츤 여섯 상황을 한·일로 한 줄씩, 모두 12줄로 만들고 Gemini 프리셋과 설계 보이스, ElevenLabs 설계·리믹스, VOICEVOX, Qwen3-TTS를 같은 대사로 블라인드 비교한다. 판정 기준은 셋이다. 어린아이처럼 들리지 않는가, 각 언어의 억양이 모국어처럼 자연스러운가, 두 언어가 같은 사람처럼 들리는가. 잡담 상주 프로세스의 첫 토큰 지연도 함께 재 둔다. TTS 첫 소리는 ElevenLabs Flash v2.5 기준 약 75 ms에 불과해 ([ElevenLabs Models](https://elevenlabs.io/docs/models)) 체감 지연은 두뇌 쪽이 좌우할 가능성이 크다(추론).

세 번째 단계는 결과에 따른 교체다. Apple의 일본어가 약하면 일본어만 parakeet-ja로, 한국어 개발 용어가 약하면 Qwen3-ASR이나 `gpt-transcribe`로 바꾼다. 청취 시험에서 "같은 사람"이 중요하게 드러나면 ElevenLabs로, 일본어의 귀여움이 더 중요하면 VOICEVOX 혼합으로 간다. 자동 언어 감지는 받아쓰기 시험의 판정 정답률이 충분할 때만 켜고, 전역 hold-to-talk와 전용 앱 번들 포장은 그다음이다. 구성별 월 비용은 다음과 같다.

| 구성 | 듣기 | 말하기 | 월 비용 추정 |
|---|---|---|---|
| 완전 로컬 | Apple 또는 whisper.cpp | Qwen3-TTS(한·일) 또는 일본어 VOICEVOX | $0 |
| 저가 혼합 | Apple | 일본어 VOICEVOX + 한국어 Gemini Flash-Lite | 약 $5 |
| 기본 권장 | Apple | Gemini 3.8 Flash(또는 Flash-Lite) | 약 $13(약 $9), 2027년 두 배 |
| 품질 우선 | `gpt-transcribe` | ElevenLabs 설계 + 리믹스, v3 합성 | 약 $32 |

말하기는 하루 300줄을 한·일 반반으로 말하는 경우(월 약 38만 자, 약 16시간 분량)에 캐시를 쓰지 않은 값이고, 듣기는 하루 10분 기준이다. 고정 대사 비중이 절반이면 말하기 비용도 절반으로 준다. 단가 출처는 앞 절과 같다.

## 결론

이번 조사로 달라진 판단은 두 가지다. 첫째, 이 기능에서 오래 남는 자산은 특정 엔진이 아니라 앱이 쥔 오디오 루프, 엔진 어댑터, 미리 렌더링한 대사 캐시다. 2026년 한 해에만 Supertone과 にじボイス가 서비스를 닫았고, ElevenLabs 로컬 MCP와 Supertonic이 아카이브됐으며, Porcupine 무료 키가 끊겼고, Gemini TTS는 내년 1월 가격을 두 배로 올린다. 음성 공급자가 1년 안에 사라지거나 조건을 바꾸는 일은 예외가 아니라 기본값이다. 그러니 엔진을 갈아 끼울 수 있는 경계와 로컬 폴백, 공급자가 사라져도 남는 대사 파일은 품질 문제가 아니라 생존 문제로 다뤄야 한다.

둘째, 후보를 가장 크게 줄이는 것은 벤치마크가 아니라 사용 방식에 대한 답 두 개다. 한 캐릭터에게 두 언어를 섞어 말하지 않는다면 자동 언어 감지는 통째로 빠지고, 캐릭터가 두 언어에서 같은 목소리일 필요가 없다면 일본어는 무료 로컬 엔진, 한국어는 저가 클라우드로 월 5달러 안팎에 끝난다. 두 답이 모두 "그렇다"일 때만 자동 감지와 리믹스한 보이스 네 개라는 가장 비싸고 복잡한 조합이 필요하다. 이 두 질문을 먼저 정하면 받아쓰기 시험과 청취 시험에서 비교할 후보가 절반으로 준다.

## 2026-09-30 사용자 결정과 그에 따른 구성

- **듣기와 말하기:**
  - 말하는 동안은 듣지 않는다(반이중).
  - 한국어 모드와 일본어 모드 중 하나를 골라 듣기와 말하기 언어를 통일한다. 자동 언어 감지는 쓰지 않는다.
- **호출어:** 음성 모드를 켜 두어도 "쵸텐짱"·"아메짱"이라고 부를 때만 반응한다.
  - 무료 한·일 호출어 엔진은 없다. 그래서 VAD로 말소리 구간만 골라 Apple 온디바이스 받아쓰기에 넣고, 앞부분이 부르는 이름과 비슷할 때만 깨운다.
  - 변형까지 받는다: 초텐짱·쵸텐쨩·超てんちゃん·ちょうてんちゃん / 아메짱·あめちゃん·雨ちゃん·飴ちゃん.
  - 이름 뒤에 이어 말한 부분은 곧바로 요청으로 받는다. 이름과 맞지 않는 말은 저장하지도, 보내지도 않고 버린다.
  - 부른 이름의 캐릭터가 답한다(아메를 부르면 변신). 이 부분은 제안이며 확정되지 않았다.
- **목소리:**
  - 유료는 쓰지 않는다. 무료만 쓰고, 품질이 낮아도 괜찮다.
  - 한 캐릭터는 두 언어에서 같은 목소리로 말하고, 초텐과 아메는 분위기를 조금 다르게 한다.
  - 이 조건을 모두 채우는 것은 로컬 Qwen3-TTS(mlx-audio)뿐이다. 캐릭터마다 VoiceDesign 설명문으로 목소리를 만들고, 짧은 레퍼런스를 Base 복제로 고정해 한·일에 같이 쓴다. M4에서의 속도는 재 봐야 한다. 네트워크가 끊겼을 때 쓸 비상용은 macOS `say`다.
- **준비 상태:** Apple 일본어(ja_JP) 받아쓰기 모델을 내려받아 두었다. 이제 설치된 언어는 ko_KR과 ja_JP다.
