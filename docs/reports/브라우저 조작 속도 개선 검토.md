# 브라우저·에이전트 조작 속도 개선 검토

2026-10-01 · skinclaude 오버레이(초텐·아메 음성 모드) · 오늘 기록과 직접 잰 값 기준

## 1. 결론

느린 이유는 브라우저가 아니라 **구조**다. 브라우저 조작 자체는 0.1~0.2초면 된다. 지금은 "변신해", "노래 멈춰" 같은 정해진 일도 매번 범용 에이전트가 처음부터 방법을 찾아내서 한다.

권고는 세 겹으로 나누는 것이다.

1. **정해진 일은 모델 없이 바로 실행한다.** 변신, 의상, 모드 전환, 노래 조작, 유튜브 재생, 사이트 열기.
2. **표현이 자유로운 요청은 도구를 쥔 빠른 모델이 한 번에 처리한다.** 모델은 "무슨 도구를 부를지"만 정하고, 실행은 오버레이가 한다.
3. **범용 에이전트(지시 모드·크롬 도우미)는 정말 여러 단계가 필요한 일에만 쓴다.**

| 요청 | 지금 (오늘 실측) | 바꾼 뒤 (예상) |
|---|---|---|
| 변신 ("雨に変身して") | 44초 | 0.1초 |
| 의상 바꾸기 | 19초 | 0.1초 |
| 노래 멈춤·다음 곡 | 10~23초 | 0.2초 |
| 유튜브에서 ○○ 틀기 | 15~47초 (길게는 135초 이상) | 3~4초 |
| 구글 검색 열기 | 16~23초 | 0.3초 |
| 날씨처럼 답만 필요한 질문 | 16~60초 | 2~6초 |

"바꾼 뒤" 값은 각 단계를 따로 잰 것을 더한 예상이다. 끝에서 끝까지 실사용으로 확인한 값이 아니다.

### 구현 현황 (2026-10-01 오후 추가)

권고 1번(의도 라우터)과 2번(유튜브 빠른 길)을 구현했고, 3번의 일부(잡담 캐릭터가 동작을 직접 실행)를 넣었다. 4·5번은 아직 하지 않았다.

| 요청 | 바꾸기 전 | 바꾼 뒤 | 확인 |
|---|---|---|---|
| 변신 | 44초 | 판정 1ms, 첫 소리 0.3초 | 실사용 |
| 의상 바꾸기 | 19초 | 판정 5~20ms, 첫 소리 0.3초 | 소리 없이 시험 |
| 유튜브에서 ○○ 틀기 | 15~47초 | 검색 0.6~1.1초, 전체 2.9~3.5초 | 실사용 여러 번 |
| 노래 멈춤 | 10~23초 | 탭 조작 0.15초 | 실사용 |
| 멈춘 노래 다시 틀기 | 28초(지시 에이전트) | 탭 조작 0.15초 | 판정만 확인, 실사용 미확인 |
| 맥 음량 | 지시 에이전트 | 0.2~0.4초 | 소리 없이 시험(같은 값으로) |
| 화면 깨우기 | 지시 에이전트 | 즉시 | 실행만 확인 |
| 하던 일 취소 | 안 됨("아직 하는 중") | 즉시 | 시험 |
| 사이트 열기 | 16~23초 | 탭 열기 0.14~0.24초 | 실제 크롬 |

- 판정은 `overlay/intent.js`, 탭 조작은 `overlay/chrometab.js`, 실행은 `overlay/main.js`의 `quickIntent`·`runIntent`.
- 지시 모드의 진짜 작업("영상 재생 버튼 추가해 줘")을 가로채지 않도록 꼴이 분명한 말만 받는다.
- 일본어 받아쓰기가 낱말을 딴 말로 적는 문제(超てん→拠点, パジャマ→風間, 変身→返信)는 발음(로마자)으로도 맞춰서 받는다.
- 15시 반에 전체 검토를 하고 판정 규칙을 다시 썼다. 평범한 말이 상태를 바꾸는 오작동("불 꺼 줘"가 노래 멈춤, "음소거가 뭐야"가 음소거, "걱정하지 마"가 작업 취소 등)이 확인돼서다. 노래 조작은 한 문장이 통째로 그 조작일 때만 받고, 골라 달라는 재생이나 딴 뜻일 수 있는 말은 지시 모드여도 잡담 캐릭터에게 보낸다.
- 잡담 모드에서는 규칙이 놓친 말도 캐릭터가 뜻을 보고 답 끝줄에 `[실행] 동작`을 붙여 바로 실행한다(잡담 답 시간 1.5~2.3초가 든다). 지시 모드에는 이 안전망이 없다.

## 3. 방법 검토

### A. 의도 라우터: 정해진 일은 모델 없이

받아쓴 문장을 짧은 규칙으로 분류해 오버레이가 바로 실행한다. 지금도 노래 조작, 재생 부탁, 모드 전환은 이 방식인데 **대화 모드에서만** 동작한다. 지시 모드에서는 전부 에이전트로 넘어간다.

- 넣을 것: 변신("아메로 변신"), 의상("기본 옷으로"), 모드 전환, 노래 조작, 유튜브 재생, 사이트 열기("유튜브 열어"), 검색 열기("구글에서 ○○ 검색").
- 모드와 상관없이 가장 먼저 본다.
- 효과가 가장 크고 작업량이 가장 작다.
- 약점: 표현이 규칙에서 벗어나면 못 잡는다. 받아쓰기 오류에도 약하다("変身" → "返信"으로 적힌 사례가 오늘 있었다). 그래서 B가 필요하다.

### B. 도구를 쥔 빠른 모델: 자유로운 표현을 한 턴에

상주하는 잡담 모델에 오버레이의 기능을 도구로 준다: `transform`, `set_costume`, `set_mode`, `play_youtube`, `media`, `open_url`, `web_search`, `ask_chrome_agent`, `run_task`. 모델은 캐릭터 말투로 한 마디 하면서 도구를 부르고, 실행은 오버레이가 한다.

- 지금의 `[크롬] 할 일` 글줄 약속을 대체한다. 글줄은 길어서 일본어 답이 279토큰(3.9초)까지 갔다.
- 예상 1.5~2.5초 (모델 두 번 왕복). Haiku로 두면 더 짧지만 오늘 시험에서 Haiku는 말투가 흔들리고 크롬 위임을 빼먹었다.
- "変身"이 "返信"으로 적혀도 문맥으로 알아듣는다.
- 약점: 구현이 A보다 크다. 도구 호출이 한 턴 더 든다.

### C. 브라우저 제어 통로 비교

| 통로 | 한 동작 시간 | 로그인된 내 크롬 | 필요한 것 | 평가 |
|---|---|---|---|---|
| Claude in Chrome 확장 (지금) | 3~11초 | 됨 | 없음 | 복잡한 일 전용으로 남긴다 |
| AppleScript 탭 조작 | 0.12초 | 됨 | 자동화 허용 (이미 됨) | 주소 열기·이동·앞으로 가져오기 |
| Apple Events 스크립트 실행 | 0.12~0.19초 | 됨 | 크롬 설정 (지금 켜짐) | **주력으로 권고** |
| 자체 크롬 확장 + 로컬 연결 | 수십 밀리초 (추정) | 됨 | 확장 설치 (개발자 모드) | 가장 강력. 2차 후보 |
| 원격 디버깅 (CDP) | 수십 밀리초 (추정) | 제한적 | 별도 프로필 또는 크롬 설정 | 기본 프로필에서는 막혀 있어 비권고 |
| 오버레이 내장 플레이어 | 즉시 | 안 됨 | 없음 | 광고·로그인 문제. 음악 전용이면 고려 |
| 미디어 키, 시스템 재생 명령 | - | - | - | 오늘 시험에서 크롬에 먹지 않음 |

원격 디버깅과 자체 확장의 지연은 재 보지 않은 추정값이다.

### D. 유튜브 빠른 길

1. 오버레이가 검색 결과를 직접 받아 첫 영상 id를 뽑는다 (0.5~0.8초).
2. 쓰던 탭의 주소를 그 영상으로 바꾼다 (0.12초). 검색 페이지를 거치지 않으니 페이지 로드가 한 번이다.
3. 탭에서 재생 여부를 확인한다 (0.15초씩).

멈춤·다음 곡·소리 조절은 탭 스크립트로 0.15초다. 캐릭터가 말할 때 플레이어 음량만 줄이는 것도 같은 방법으로 된다(맥 음량을 건드리지 않아 더 깔끔하다).

- 약점: 검색 결과 파싱은 비공식이라 유튜브가 구조를 바꾸면 깨진다. 실패하면 크롬 도우미로 넘기는 대비가 필요하다.
- 검색을 거치는 직접 재생 코드는 이미 들어 있다. 설정이 꺼져 있던 동안 만들어서 실사용 검증이 안 됐다.

### E. 답만 필요한 질문은 브라우저를 거치지 않는다

"오늘 날씨 어때"는 화면이 아니라 답이 필요하다.

- 날씨·환율·시각 같은 건 API로 0.3초에 받고 모델이 한 문장으로 말한다.
- 그 밖의 질문은 모델에 웹 검색 도구를 준다 (2~6초 예상).
- "구글에서 ○○ 검색해 줘"처럼 화면을 원할 때만 크롬을 연다 (0.3초).

### F. 범용 에이전트 자체를 빠르게

에이전트가 꼭 필요한 일에도 지금은 낭비가 있다.

- **안내서**: 작업 폴더에 `CLAUDE.md`를 두고 오버레이 주소(`/form`, `/costume`), 크롬 조작 방법, 쓰던 탭을 적어 둔다. 오늘 에이전트는 이걸 찾느라 요청마다 15~40초를 썼다.
- **상주**: 잡담처럼 프로세스를 띄워 두면 기동 1.5초와 첫 응답 지연이 줄어든다.
- **모델**: 간단한 지시는 Sonnet, 생각 끄기. 오늘 잡담에서 생각을 끄자 첫 글자가 3~14초에서 0.6~1.1초가 됐다.
- **문맥**: 도구를 필요한 것만 싣고, 크롬 도우미 세션(지금 7만 7천 토큰)은 주기적으로 새로 연다.

### G. 음성 앞단

- 지금 말 끝에서 확정까지 0.8초다. 정해진 명령은 더 일찍 실행할 수 있다(부분 결과로 미리 시작). 다만 Apple 받아쓰기는 부분 결과를 실시간으로 주지 않아서 빠른 모드로 바꿔야 하고, 그러면 이름 인식이 나빠진다. 얻는 것(0.3~0.5초)에 비해 위험이 커서 **후순위**다.

### H. 체감 속도

- 즉시 한 마디, 진행 중 비프음, 결과 한 문장 읽기는 이미 들어 있다.
- 남은 것: 에이전트가 오래 걸릴 때 중간 상황을 한 마디로 알리기.

### I. 시스템

- 스왑을 8.4GB 쓰고 있다(16GB 맥). 안드로이드 에뮬레이터가 10일 넘게 1.2GB를 쥐고 있다. 이 때문에 목소리 엔진 준비가 3분 걸린 적이 있다.
- 모델 응답과 브라우저 조작에는 영향이 작지만, 목소리 합성과 받아쓰기에는 영향이 있다.

## 5. 위험과 주의

- **크롬 설정**: "Apple Events의 자바스크립트 허용"은 자동화 권한을 받은 앱이 로그인된 탭 안에서 스크립트를 돌릴 수 있게 한다. 지금 그 권한이 있는 건 오버레이(Electron)와 지시 모드 에이전트가 쓰는 터미널 경로다.
- **오인식**: 규칙으로 바로 실행하면 잘못 알아들은 말도 바로 실행된다. 되돌릴 수 있는 일(변신, 재생, 멈춤)만 규칙에 넣고, 보내기·결제 같은 일은 지금처럼 확인을 거친다.
- **비공식 파싱**: 유튜브 검색 결과 구조가 바뀌면 깨진다. 크롬 도우미로 넘기는 대비를 둔다.
- **자동 재생**: 탭 주소만 바꿨을 때 재생이 시작되는지는 크롬의 자동 재생 정책에 달려 있다. 오늘 도우미가 같은 방식으로 재생한 기록은 있지만, 창이 가려져 있으면 안 됐다.

## 6. 확인하지 못한 것

- 탭 직접 재생의 끝에서 끝까지 시간. 단계별로만 쟀다.
- 자체 확장과 원격 디버깅의 실제 지연.
- 잡담 모델에 도구를 줬을 때의 실제 왕복 시간.
- 지시 모드 마지막 요청에서 "재생이 몇 초 뒤 저절로 멈춘다"는 현상의 원인. 에이전트가 조사하던 중이었고, 오버레이의 소리 줄이기와 관련 있는지 보지 못했다.
